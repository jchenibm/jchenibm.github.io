01 · 为什么需要

从 Prompt Engineering 到 Loop Engineering

过去两年，使用 AI Agent 的方式是「写好 prompt → 看结果 → 写下一个 prompt → 再看」——你全程握着一个工具，Agent 只是一个响应者。这个模式的根本问题：你成了调度瓶颈。

Loop Engineering 是一种工作范式的迁移：你不再扮演「逐轮提示 Agent 的人」，而是设计「那个会自动提示 Agent 的系统」。Claude Code 负责人 Boris Cherny 说——"我不再提示 Claude，我写 Loop"。

Prompt Engineering

  • 杠杆点：每轮提示的质量
  • 人的角色：操作工
  • Agent 角色：响应者
  • 价值来源：你说了什么
  • 难度：写好一段话

Loop Engineering

  • 杠杆点：系统架构的设计质量
  • 人的角色：产线设计师
  • Agent 角色：自主执行者
  • 价值来源：你设计了什么
  • 难度：设计一个系统
好的循环把工程判断制度化，坏的循环把混乱自动化。真正的 loop 往往不是最开放的，而是最有边界的。

三层架构：Loop 坐在 Harness 之上，Harness 包裹 Agent

02 · 六大原语

Loop Engineering 的六个构建块

Codex 和 Claude Code 的原语几乎一一对应——这是工具无关的通用模式。六个全齐，loop 才能真正无人值守运行。

Loop 的六大原语围绕中心协同运作，缺一不可

原语职责Claude Code 实现缺了会怎样
Automations心跳——定时发现+分诊/loop /goal cron hooks一次性运行，不是 loop
Worktrees隔离——并行不冲突git worktree isolation: worktree并行 Agent 互相覆盖文件
Skills意图外部化SKILL.md 插件打包每轮从零推导整个项目

03 · 配置体系

Claude Code 的 Loop Engineering 配置

Claude Code Loop Engineering 的完整文件结构

Harness 配置：CLAUDE.md

CLAUDE.md 在每次会话启动时自动注入，为 Agent 提供身份、规则和上下文。保持在 80 行以内——有了它，loop 开始有复利。

💡 设计要点

全局 CLAUDE.md 放在 ~/.claude/CLAUDE.md，项目级放在项目根目录。项目级覆盖全局。两层协同：全局定义通用规则，项目级定义特定上下文（技术栈、构建命令、代码规范）。

~/.claude/CLAUDE.md — 全局配置示例

# ABOUT YOU

04 · Maker-Checker 分离

Sub-agents：Loop 中最有杠杆的一步

写代码的模型给自己的代码打分，就像学生给自己的考试阅卷——太宽容了。Loop 无人值守时，可信的 verifier 是你唯一能放心走开的理由。

Explorer → Implementer → Reviewer 流水线，Reviewer 不通过时触发新一轮修复

Agent 定义格式

在 ~/.claude/agents/ 下创建 Markdown 文件，使用 YAML frontmatter：

---
name: explorer                      # 必填，Agent 唯一标识
description: "只读探索 Agent"         # 必填，用途和触发场景
model: haiku                        # opus | sonnet | haiku
tools: Read, Grep, Glob, LSP, WebSearch  # 可选工具列表
---
# Agent 指令（Markdown 正文）
👁

Explorer

haiku 只读

快速扫描代码库、搜索模式、分析依赖关系。输出结构化发现供下游消费。

成本约 Opus 的 1/20，高频低风险操作

🔨

Implementer

opus 读写

深度推理，完整读写和执行权限。实现功能、修复 bug、重构代码。

核心生产者，需要最强推理能力

🔍

Reviewer

opus 只读+Adversarial

对抗性审查——默认立场是"这里有问题"。检查正确性、安全性、接口兼容。

质量守门员，审查者不修改代码

⚠️ 为什么 Reviewer 只读？

审查者不修改代码——避免既当裁判又当运动员。你的工作是指路，不是代驾。这是 Loop 无人值守可信运行的唯一保障。

05 · Skills & Connectors

意图外部化与工具接入

Skills：Loop 的复利效应

没有 skills，loop 每轮从零推导整个项目。有 skills，意图写在外面，约定/构建步骤/历史教训写一次，每次运行 agent 都读到——loop 开始有复利。

~/.claude/skills/triage/SKILL.md

---
name: triage
description: "每日项目 triage。扫描 CI 失败、open issues、lint 警告。"
---

# 每日 Triage 流程

## Step 1：读取状态
读取 AGENTS.md 获取上次 triage 的进度。

## Step 2：扫描问题
- CI 失败: gh run list --status failure --limit 5
- Open Issues: gh issue list --state open --limit 20
- Lint 警告: golangci-lint run ./...

## Step 3：分类
- 可自动修复（低风险）→ 派 implementer agent
- 需人工判断（高风险）→ 记录到 AGENTS.md

Connectors：MCP Servers

Connectors 让 Agent 能操作你的真实工具链——GitHub、数据库、Slack、CI/CD。

06 · 自动化与状态

Automations + State：让 Loop 转起来

三种定时触发方式

⏱

/loop

Claude Code 内置。每 N 分钟运行一次，支持动态间隔。适合交互式场景。

/loop 5m /triage
📋

CronCreate

在对话中创建定时任务，可持久化到磁盘，跨会话存活。

cron: "57 8 * * 1-5"
durable: true
🚀

GitHub Actions

CI/CD 集成。适合无人值守、服务器端执行。支持 workflow_dispatch 手动触发。

claude-code-action@v1
prompt: "每日 triage..."

State：Agent 遗忘，仓库不忘

The agent forgets, the repo doesn't. Agent 每次启动都是白纸一张。Loop 能跨会话持续运转，唯一的依赖是外部状态。

项目根目录/AGENTS.md — 状态文件

# AGENTS.md — Payment Service 状态

## 最近一次 Triage
- 日期：2026-06-13
- 处理的问题数：7
- 自动修复数：4（3 个 PASS，1 个 REQUEST_CHANGES）

## 进行中
- [ ] JWT Token 验证中间件
  - 状态：代码已写完，等待 review
  - 文件：src/middleware/auth.go

## 技术债记录
- src/handler/user.go:L45 — 错误处理需要细化

## 已知的坑
- PostgreSQL timestamp 精度 vs Go time.Time 精度
✓ 关键原则

每次 loop 启动时，第一个动作就是读取 AGENTS.md——从上次的进度接着来，而不是从零开始。这个机制简单到容易被忽视，但它是所有长运行 Agent 的共同依赖。

07 · 实战案例

构建一个每日自动 Triage Loop

场景：你维护一个 Go 微服务项目。每天早上 9 点自动扫描 CI 失败、issue、lint 警告，低风险问题自动修复并提 PR，高风险问题推送到 triage inbox。

每日 Triage Loop 完整执行时间线（08:57 → 09:15，约 18 分钟）

GitHub Actions 配置

.github/workflows/daily-triage.yml

name: Daily Triage
on:
  schedule:
    - cron: '50 1 * * 1-5'   # UTC → 北京时间 9:50
  workflow_dispatch:

jobs:
  triage:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - name: Run Triage Loop
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            执行每日 triage：
            1. 读取 AGENTS.md 获取上次状态
            2. 用 explorer sub-agent 扫描 CI 和 issues
            3. 对低风险问题 spawn implementer (worktree)
            4. 对每个修复 spawn reviewer (adversarial)
            5. 通过的自动开 PR，不通过的记录技术债
            6. 更新 AGENTS.md

进阶模式：PEV 循环

Loop 的每一轮迭代本质上是一个 Plan-Execute-Verify 循环：

Plan

将需求转化为操作契约——做什么、不改什么、完成标准

Execute

在隔离环境中运行——worktree、分级权限、沙盒

Verify

静态分析 + 动态测试作为确定性传感器

每次修改都应该可观测、可回滚。测试失败必须修复，高危操作必须人类审批。

08 · 风险与警示

Loop 越强，三个风险越尖锐

Loop 改变了工作方式但没有消除人的责任。随着 Loop 能力增强，三个问题不是变轻松了，而是变得更尖锐：

🔴 验证负担

无人值守的 loop 也无人值守地犯错。"done" 是声明而非证明。

→ Reviewer adversarial 指令 + 结构化审查报告 + 人类定期抽查

🟡 理解债务

Loop 越快地产出你没读过的代码，你对该代码库的理解就越脱离实际。

→ 每周固定时间阅读 loop 产出的代码

🔵 认知缴械

当系统自动运行时，停止思考、全盘接受的诱惑极大。三个风险形成恶性循环。

→ 有意识地在 Loop 之外维持对代码库的深度理解

同一个 Loop，两个人跑可以出完全不同的结果。一个用它深化自己理解的工作加速前进，另一个用它逃避理解。Loop 不知道区别。你知道。

三个风险互相强化，形成恶性循环

09 · 落地检查清单

你的 Loop 准备好了吗

  • CLAUDE.md 写好了吗（全局 + 项目级，<80 行）
  • AGENTS.md 创建了吗（初始状态文件）
  • 三个 Agent 定义了吗（explorer / implementer / reviewer）
  • Agent 的 model 和 tools 选对了吗
  • MCP connectors 配置了吗（GitHub、数据库等）
  • 定时触发配好了吗（cron / GitHub Actions）
  • Stop hook 配置了吗（循环拦截）
  • 完成信号定义了吗（DONE / ABORT / PAUSE）
  • 验证命令确认能跑通吗（build / test / lint）
  • 风险接受了吗（你理解这三个警示吗）
下一步

完成所有检查项后，运行你的第一个 Loop：/loop 5m /triage。观察一轮完整流程，确认 explorer → implementer → reviewer 流水线正常运转。
