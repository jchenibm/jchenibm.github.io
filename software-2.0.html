01核心概念

什么是 Software 2.0？

很多人将神经网络视为"机器学习工具箱中的另一个工具"，但这完全错过了森林，只看到了树木。神经网络不仅仅是另一个分类器，它们代表了软件开发方式的根本性转变的开始——这就是Software 2.0。

神经网络不是另一个分类器，它们代表了软件开发方式的根本性转变的开始。

— Andrej Karpathy

Software 1.0是我们都熟悉的经典技术栈——用 Python、C++ 等语言编写。它由程序员编写的显式指令组成，程序员通过编写每一行代码，在程序空间中识别具有特定行为的点。

Software 2.0则是用更抽象的、对人类不友好的语言编写的——比如神经网络的权重。没有人参与编写这些"代码"，因为有大量的权重（典型的网络可能有数百万个），直接用权重编码相当困难。

在 Software 2.0 中，我们的方法是：

  • 指定目标：定义理想程序的行为（例如"满足数据集的输入输出对"或"赢得围棋游戏"）
  • 编写骨架：编写代码的粗略骨架（即神经网络架构），识别程序空间的子集进行搜索
  • 搜索优化：使用计算资源搜索该空间以找到有效的程序
02编译过程对比

从源代码到二进制

Software 1.0：人工编写的源代码（如 .cpp 文件）被编译成执行有用工作的二进制文件。

Software 2.0：源代码通常包括：

  • 数据集：定义理想行为
  • 神经网络架构：提供代码的粗略骨架，但有许多细节（权重）需要填充

训练神经网络的过程将数据集"编译"成二进制——最终的神经网络。

关键洞察

在大多数实际应用中，神经网络架构和训练系统正日益标准化为商品。因此，大部分主动的"软件开发"采用策划、增长、处理和清理标记数据集的形式。

这从根本上改变了我们迭代软件的编程范式，团队分裂为两部分：

  • 2.0 程序员（数据标注员）编辑和增长数据集
  • 1.0 程序员维护和迭代周围的训练代码基础设施、分析、可视化和标注界面
03持续转型的领域

从 1.0 到 2.0 的迁移

大量现实世界问题具有这样的属性：收集数据（或识别理想行为）比显式编写程序要容易得多。因此，我们正在见证大规模的行业转型，大量 1.0 代码被移植到 2.0 代码中。

  • 视觉识别：从工程特征 + 机器学习 → 大数据集 + 卷积神经网络架构搜索 → 架构搜索
  • 语音识别：预处理 + 高斯混合模型 + 隐马尔可夫模型 → 几乎完全的神经网络
  • 语音合成：各种拼接机制 → 大型 ConvNet（如 WaveNet）产生原始音频信号输出
  • 机器翻译：基于短语的统计技术 → 神经网络快速占主导地位
  • 游戏：显式手写的围棋程序 → AlphaGo Zero（查看原始棋盘状态的 ConvNet）
  • 数据库：传统索引结构 → 学习索引结构（神经网络替代核心组件）
趋势洞察

Google 目前处于将自身大量代码重写为 Software 2.0 代码的最前沿。"One Model to Rule Them All"提供了这可能的样子草图，其中各个领域的统计强度被整合为一个一致的世界理解。

04Software 2.0 的优势

为什么选择 2.0？

显然，一个简单的答案是它们在实践中工作得更好。但还有很多其他方便的理由选择这个技术栈：

  • 计算上同质：典型的神经网络主要由两种操作组成——矩阵乘法和零阈值。与经典软件的指令集相比，更容易提供各种正确性/性能保证。
  • 易于集成到硅中：由于神经网络指令集相对较小，更容易在硬件层面实现，如自定义 ASIC、神经形态芯片等。
  • 恒定的运行时间：每次神经网络前向传播迭代花费完全相同的 FLOPS。没有基于代码执行路径的可变性。
  • 恒定的内存使用：没有动态分配的内存，几乎没有交换到磁盘的可能性，也没有内存泄漏需要追踪。
  • 高度可移植：与经典二进制文件或脚本相比，矩阵乘法序列更容易在任意计算配置上运行。
  • 非常敏捷：可以通过移除一半通道、重新训练来使程序速度提高一倍。相反，如果获得更多数据/计算资源，可以通过添加更多通道并重新训练来立即改进程序性能。
  • 模块可以融合为最优整体：如果两个最初分别训练的 Software 2.0 模块交互，我们可以轻松地通过整个反向传播。这是默认行为。
  • 比你更好：最重要的是，神经网络在许多有价值的垂直领域中是比你我都能想出的更好的代码。
05Software 2.0 的局限性

需要权衡的方面

2.0 技术栈也有一些自身的劣势：

  • 可解释性差：优化结束后，我们剩下的大型网络工作良好，但很难解释如何工作。在许多应用领域，我们将面临使用我们理解的 90% 准确的模型，或不理解的 99% 准确的模型之间的选择。
  • unintuitive 的失败方式：2.0 技术栈可能以不直观和令人尴尬的方式失败，或者更糟糕的是，它们可能"静默失败"——例如，默默采用训练数据中的偏见，这些偏见很难在规模通常为数百万的情况下正确分析和检查。
  • 对抗性示例：对抗性示例和攻击的存在突显了该技术栈的非直观性质。
挑战

我们仍在发现这个技术栈的一些特殊属性。理解这些局限性对于在实践中有效部署 Software 2.0 解决方案至关重要。

062.0 技术栈中的编程

新的开发工具链

Software 1.0 是我们编写的代码。Software 2.0是基于评估标准（如"正确分类训练数据"）由优化编写的代码。

任何程序不明显但可以重复评估其性能的设置（例如——你是否正确分类了某些图像？你是否赢得了围棋游戏？）都将受到这种转型的影响，因为优化可以找到比人类能编写的更好的代码。

工具链缺口

我们为人类编写 1.0 代码构建了大量工具（IDE、语法高亮、调试器、分析器、git 集成等）。在 2.0 技术栈中，编程是通过累积、处理和清理数据集来完成的。

需要的工具：

  • 第一个 Software 2.0 IDE，帮助处理累积、可视化、清理、标注和采购数据集的工作流
  • Software 2.0 Github，其中仓库是数据集，提交由标签的添加和编辑组成
    • >传统包管理器和相关服务基础设施（pip、conda、docker 等）帮助我们更有效地部署、共享、导入和使用 Software 2.0 二进制文件
07未来展望

AGI 的编程范式

在短期内，Software 2.0 将在以下领域变得日益普遍：

  • 重复评估可能且便宜的场景
  • 算法本身难以显式设计的领域

长期来看，这个范式的未来是光明的，因为越来越清楚的是，当我们开发 AGI 时，它肯定会用 Software 2.0 编写。

关键结论

Software 1.0 正在吞噬世界，而 AI（Software 2.0）正在吞噬软件。

需要构建的生态系统：

  • 数据集管理和版本控制
  • 神经网络部署和服务基础设施
  • 模型监控和可观测性工具
  • 数据标注和质量保证工具
  • 模型解释和调试工具
