驾驭工程

为了让编码代理在更少监督下工作，我们需要建立对其结果信任的机制。作为软件工程师，我们对 AI 生成的代码有着天然的信任障碍——LLM 是非确定性的，它们不了解我们的上下文，也不真正理解代码，它们以 token 为思考单位。本文探索了一个思维模型，整合了上下文工程和驾驭工程中的新兴概念，以构建这种信任。

定义 · 01

什么是 驾驭

"驾驭"已成为 AI 代理中除模型本身以外所有内容的简称。
点击展开

Agent = Model + Harness

这是一个非常宽泛的定义，因此有必要针对常见类别的代理进行缩小范围。在编码代理的上下文中，我将其定义为：

  • 内置驾驭：部分驾驭已内置在编码代理中（如系统提示词、代码检索机制、复杂的编排系统）
  • 外部驾驭：编码代理为用户提供的功能，用于针对特定用例和系统构建外部驾驭层

一个构建良好的外部驾驭层有两个目标：

  • 提高代理首次就做对的概率
  • 提供反馈循环，让问题在到达人眼之前尽可能自我修正

隐喻的局限

"你有没有试过给狗的内侧套上挽具？"
点击展开

关键要点：隐喻的价值在于实用性，而非精确性。如果"驾驭"这个概念能帮助我们思考如何控制 AI 代理，那么它就是有用的。

控制论 · 03

控制论调节器

代理驾驭像一个控制论调节器，结合前馈和反馈将代码库调节到期望状态。
点击展开

代理驾驭充当控制论调节器的角色：

  • 前馈控制：预判不良输出并尝试预防
  • 反馈控制：观察代理行动后的结果，帮助其自我修正

只有前馈的代理会重复同样的错误；只有反馈的代理会编码规则但永远不知道是否有效。两者结合才能创建真正的自修正系统。

引导器 Guides

预判代理行为并旨在其行动前进行引导。
点击展开

引导器是前馈控制机制，它们：

  • 在代理行动前预判其行为
  • 旨在引导代理在首次尝试时就创建良好结果
  • 提高代理首次就做对的概率

示例：

  • 编码约定（AGENTS.md、Skills）
  • 项目启动指南
  • 代码修改工具（如 OpenRewrite）

反馈 · 02

传感器 Sensors

在代理行动后观察并帮助其自我修正。
点击展开

传感器是反馈控制机制，它们：

  • 在代理行动后观察结果
  • 帮助代理自我修正
  • 当产生为 LLM 消费优化的信号时特别强大

特别有效的形式：

包含自我修正指令的自定义 linter 消息——一种积极的"提示注入"。

示例：

  • 结构化测试（ArchUnit 模块边界检查）
  • 代码审查指南
  • 类型检查器

类型 · 03

计算型 Controls

确定性和快速，由 CPU 运行。
点击展开

计算型控制具有以下特征：

  • 确定性：结果可靠
  • 快速：毫秒到秒级运行
  • 低成本：由 CPU 运行

示例：

  • 测试（单元测试、集成测试）
  • Linter（代码风格检查）
  • 类型检查器（TypeScript、mypy 等）
  • 结构分析（依赖分析、复杂度分析）

优势：计算型引导器通过确定性工具提高良好结果的概率。计算型传感器足够便宜和快速，可以在每次变更时与代理并行运行。

关联概念
parallels ↔ 推理型 feeds → 每次变更检查
类型 · 04

推理型 Controls

语义分析，"LLM 作为判断者"。
点击展开

推理型控制具有以下特征：

  • 语义分析：理解代码意图和上下文
  • AI 代码审查：使用 LLM 评估代码质量
  • "LLM 作为判断者"：让模型评估其他模型的输出
  • 较慢且昂贵：通常由 GPU 或 NPU 运行
  • 非确定性：结果更不确定

优势：尽管具有非确定性，但当我们使用适合任务的强模型时，推理型传感器可以特别增加我们的信任。

它们允许我们既提供丰富的引导，又添加额外的语义判断。

示例：

  • AI 代码审查（语义理解）
  • 技能指令（自然语言指导）
  • 代码相似度分析（语义级别）

02调节循环
迭代改进

转向循环

人类在驾驭工程中的角色：通过迭代驾驭来引导代理
人类角色 · 01

转向循环 Steering Loop

人类的工作是通过迭代驾驭来引导代理。
点击展开

转向循环的核心思想：

每当问题多次发生时，应该改进前馈和反馈控制，使该问题在未来发生的概率降低，甚至完全预防。

循环流程：

  1. 发现问题：代理重复犯错
  2. 分析根因：理解为什么控制没有捕获问题
  3. 改进控制：增强前馈引导或反馈传感
  4. 验证效果：观察问题是否减少

使用 AI 改进驾驭：

在转向循环中，我们当然也可以使用 AI 来改进驾驭本身。编码代理现在使得构建更多自定义控制和自定义静态分析变得更加便宜：

  • 代理可以帮助编写结构化测试
  • 从观察到的模式生成规则草案
  • 搭建自定义 linter
  • 从代码库考古创建操作指南

时机 · 02

质量左移 Keep Quality Left

将检查尽可能放在生产路径的左侧。
点击展开

持续集成的挑战：

持续集成的团队一直面临将测试、检查和人工审查分布在开发时间轴上的挑战，根据其成本、速度和关键性来决定。

质量左移原则：

当你渴望持续交付时，你甚至希望每个提交状态都可部署。你希望检查尽可能放在通往生产路径的左侧，因为越早发现问题，修复成本越低。

反馈传感器的分布：

包括新的推理型传感器在内的反馈传感器，需要相应地分布在生命周期中。

四个关键问题：

  1. 什么足够快，应该在集成前甚至创建提交前运行？（如 linter、快速测试套件、基本代码审查代理）
  2. 什么更昂贵，因此只应在集成后的管道中运行？（如变异测试、更广泛的代码审查）
  3. 什么样的漂移会逐渐积累，应该由在变更生命周期外持续运行的传感器监控？（如死代码检测、测试覆盖率分析、依赖扫描器）
  4. 代理可以监控什么运行时反馈？（如监控降级的 SLO、AI 判断持续采样响应质量）

03调节分类
控制维度

调节类别

三种驾驭类型：可维护性、架构适配性和行为
类别 · 01

可维护性 驾驭

调节内部代码质量和可维护性。
点击展开

可维护性驾驭是目前最容易实现的驾驭类型，因为我们有大量可使用的现有工具。

计算型传感器可靠捕获：

  • 重复代码
  • 圈复杂度
  • 缺失的测试覆盖
  • 架构漂移
  • 风格违规

这些是便宜、经过验证且确定性的。

推理型控制部分解决：

  • 语义重复代码
  • 冗余测试
  • 暴力修复
  • 过度工程解决方案

但昂贵且概率性，不能在每次提交时运行。

都无法可靠捕获：

  • 问题误诊
  • 过度工程和不必要的功能
  • 误解指令

它们有时会捕获，但不够可靠，无法减少监督。如果人类没有首先清楚地指定他们想要什么，正确性就在任何传感器的范围之外。

类别 · 02

架构适配性 驾驭

定义和检查应用程序的架构特征。
点击展开

架构适配性驾驭将定义和检查应用程序架构特征的引导器和传感器分组。

基本上就是：适应度函数。

示例：

  • 性能：前馈我们的性能要求的技能，以及反馈代理是否改进或降级它们的性能测试
  • 可观测性：描述更好可观测性的编码约定（如日志标准）的技能，以及要求代理反思其可用日志质量的调试指令

这些检查确保代码符合架构设计的性能要求和可观测性标准。

类别 · 03

行为 驾驭

房间里的大象：功能行为如何引导和感知？
点击展开

行为驾驭是房间里的大象——我们如何引导和感知应用程序在功能上是否按我们需要的方式运行？

当前主流方法：

目前大多数给编码代理高自主权的人这样做：

  • 前馈：功能规范（从简短提示到多文件描述的不同详细级别）
  • 反馈：检查 AI 生成的测试套件是否通过、是否有合理的高覆盖率、有些人甚至通过变异测试监控其质量。然后结合手动测试

问题：

这种方法对 AI 生成的测试寄予了太多信心，这还不够好。

一些同事在"批准的夹具模式"（approved fixtures pattern）中看到了好结果，但它在某些领域比其他领域更容易应用。他们选择性地在适合的地方使用它，这不是测试质量问题的全面答案。

结论：

总的来说，我们还有很多工作要做，以找出功能行为的良好驾驭，这些驾驭能足够增加我们的信心，减少监督和手动测试。

03实践要点
实施考虑

可驾驭性

环境属性：让代码库更容易被驾驭
环境 · 01

可驾驭性 Harnessability

不是每个代码库都同样易于驾驭。
点击展开

可驾驭性差异：

用强类型语言编写的代码库自然有类型检查作为传感器；清晰可定义的模块边界提供架构约束规则；像 Spring 这样的框架抽象了代理甚至不需要担心的细节，因此隐式地增加了代理成功的机会。

没有这些属性，这些控制就不可用于构建。

环境提供的能力（Ambient Affordances）：

我的同事 Ned Letcher 用"环境提供的能力"这个术语来描述使代理环境更可驾驭的属性：

"环境本身的结构属性，使其在内部操作的代理可读、可导航和可处理。"

绿地 vs 遗留：

  • 绿地团队：可以从第一天就嵌入可驾驭性——技术决策和架构选择决定了代码库将有多可治理
  • 遗留团队：面临更困难的问题——尤其是在积累了大量技术债务的应用中，驾驭最需要的地方也最难构建

模板 · 02

驾驭模板

服务拓扑演变为驾驭模板的潜力。
点击展开

服务拓扑到驾驭模板：

大多数企业都有几种常见的服务拓扑，覆盖了他们 80% 的需求——通过 API 暴露数据的业务服务；事件处理服务；数据仪表板。

在许多成熟的工程组织中，这些拓扑已经在服务模板中编纂成文。这些可能会在未来演变为驾驭模板：

驾驭模板 = 引导器和传感器的捆绑包

它将编码代理束缚到拓扑的结构、约定和技术栈上。

团队可能会根据哪些驾驭已经可用，部分地基于此来选择技术栈和结构。

挑战：

我们当然会面临与服务模板类似的挑战。一旦团队实例化它们，它们就开始与上游改进不同步。驾驭模板将面临相同的版本控制和贡献问题，考虑到非确定性的引导器和传感器更难测试，这可能更糟。

定律 · 03

Ashby 定律

必要多样性定律：调节器必须具有至少与被调节系统一样多的多样性。
点击展开

Ashby 定律（必要多样性定律）：

定律说调节器必须具有至少与被调节系统一样多的多样性，它只能调节它有模型的东西。

对驾驭模板的启示：

  • 基于 LLM 的编码代理几乎可以产生任何东西
  • 但承诺拓扑会缩小那个空间，使全面的驾驭更可实现
  • 定义拓扑是一种多样性减少的举措

关键洞察：

通过预定义的拓扑，我们限制了代理可以产生的输出空间，这使得构建全面的驾驭系统变得更加可实现。这是 Ashby 定律在实际工程中的应用。

角色 · 04

人类角色

驾驭是人类开发者经验的外化和显式化。
点击展开

人类开发者带来的隐性驾驭：

作为人类开发者，我们将技能和经验作为隐性驾驭带到每个代码库：

  • 我们吸收了约定和良好实践
  • 我们感受到了复杂性的认知痛苦
  • 我们知道我们的名字在提交上
  • 我们承载着组织一致性——团队试图实现什么、哪些技术债务因业务原因被容忍、在这个特定上下文中"好"是什么样子的
  • 我们以小步和人类速度前进，这创造了经验被触发和应用的思考空间

编码代理缺乏的：

编码代理没有这些：

  • 没有社会问责
  • 没有对 300 行函数的美学厌恶
  • 没有直觉知道"我们不在这里这样做"
  • 没有组织记忆
  • 不知道哪个约定是承重的，哪个只是习惯
  • 不知道技术上正确的解决方案是否符合团队试图做的事情

驾驭的局限性：

驾驭是试图外化和显式化人类开发者经验带来的东西，但它只能走到这一步。

构建一个连贯的引导器、传感器和自修正循环系统是昂贵的，所以我们必须带着明确的目标进行优先级排序：

好的驾驭目标：

不一定旨在完全消除人类输入，而是将人类输入引导到我们输入最重要的地方。

04结论
总结

思维模型

从功能层面提升到战略性系统设计
愿景 · 01

超越功能

将对话提升到技能和 MCP 服务器之上。
点击展开

思维模型的目标：

我在这里概述的思维模型描述了实践中已经在发生的技术，并帮助构建关于我们仍然需要弄清楚的事情的讨论。

提升对话层次：

它的目标是将对话提升到功能层面以上——从技能和 MCP 服务器到我们如何战略性地设计一个真正给予我们对代理产出的信心的控制系统。

核心思想：

驾驭工程不是关于单个功能或工具，而是关于设计一个整体的控制系统，这个系统能够：

  • 在问题发生前预防它们
  • 在问题发生后自动修正它们
  • 将人类注意力引导到最重要的地方
  • 持续改进和适应
